# Match Capture / Match-History Notes

Working notes from the 2026-06-17 investigation. Companion to `docs/nettable.md`
(which has the full per-table raw dumps and the F-key capture matrix). Come back
to this for the *decisions and field semantics*, not the raw schemas.

---

## 1. Drodo match history is a dead end (do not keep chasing)

The in-game "match history" panel (the per-player list of recent games) is **not
externally obtainable**. Full trace:

- It lives in the `match_history_table` CustomNetTable, key `match_history_<playerSlot>`,
  read by the UI via `CustomNetTables.GetTableValue(...)` (`panorama/scripts/custom_game/dac.vjs_c`,
  `UpdateRankingSelf`). It reads **only the local player's** slot.
- The value is **too big for the engine string table**, so it's delivered out-of-band
  to Panorama. `dumpstringtable` returns **zero bytes** for it (proven: 83 KB single
  entries dump fine, this one dumps empty even element-scoped). So our backend, which
  reads `dumpstringtable` output, can never see it.
- `GetTableValue` is Panorama JS only — **no console command**, can't call it externally.
- It originates from Drodo's `/game/new/@<steamids>` response (`user_info.match_history`),
  which is **server-key gated** (`GetSendKey()` / `GetDedicatedServerKeyV2`) and starts a
  game. Server keys are generated by Valve's dedicated-server infra, unforgeable, and a
  self-hosted lobby returns `Invalid_NotOnDedicatedServer`. Never obtainable.
- `courier/get/@<steamid>` (what we already poll) has **no** match history — only
  `match_s43`/`match_s42` (counts), MMR, candy, queen_rank, etc. Confirmed against raw
  `drodo_raw_data`.
- The old clean REST API (`autochess.varena.com/api/autochess/player/{id}/matches/`) was
  **VPGame/VPEsports'** third-party frontend, not Drodo's. It died when DAC moved to the
  Chinese Dragonest/ppbizon backend. Every public DAC tracker died with it. ppbizon
  exposes no public match endpoint (≈40 paths probed, all 404).
- Demo route is dead too: `record` is cheat-gated (`sv_cheats` is server-side, can't
  override), and the addon's anti-cheat (`addon_game_mode.lua:2742`) ends the game
  ~5 s after cheats are enabled (`CHEAT MODE! BYEBYE`).
- Wayback has varena archived (2019 match pages with embedded `__NEXT_DATA__`) — usable
  only as a frozen 2019 research dataset, **not** current/personal data.

**Conclusion:** the only history we can ever have is what we capture forward ourselves
(`end_board` → `matches`). Stop spending on backfill / Drodo integration.

### Strategy note
- One observer captures the **whole lobby** (all 8 boards live in the nettable), not just
  themselves. Top Queen pool is small and overlapping → a handful of high-rank installs ≈
  near-complete top-tier coverage. Target a few whales / one Queen streamer, not the
  Chinese mass market (unreachable: no S2S with Drodo, language barrier).

## 2. `end_board` (F21/`dac_table`) vs `player_info_table` (F22)

Both hold a per-player object with the **same 46 keys** (identical schema). The
distinction is timing/finalization, not shape.

- **`player_info_table.player_info`** (F22, on round change) = the live current player
  state. Re-dumped every round → use for the per-round timeline.
- **`dac_table.end_board`** (F21, POST_GAME burst) = the server's single atomic final
  write of all 8 players.

In one full game compared: **6 of 8 players byte-identical** between the two tables.
Only the **survivors** (1st, 2nd — still alive at the buzzer) differ, in exactly the
post-game settlement fields:

| key | end_board | player_info_table |
|---|---|---|
| `delta` (MMR change) | `62` / `42` | **key absent** |
| `level_delta` | `0` / `1` | **key absent** |
| `mmr_level` | final (e.g. 20) | stale (19) |
| `candy_award` | real | `0` |
| `candy` | this-game award | lifetime total |

**Why:** MMR/reward settlement is computed at game conclusion and written only to
`end_board`. Eliminated players already have it (locked when they died); survivors never
get it in the live table.

**Decision:** `end_board` is mandatory ONLY for the top finishers' MMR/reward settlement
(`delta`, `level_delta`, `mmr_level`, `candy_award`). Everything else is reconstructable
from the last `player_info_table` dump. So: must reliably catch `end_board`.

### `dac_table` top-level keys (vs `player_info_table`'s single `player_info`)
- `end_board` — the real prize (above).
- `player_info` — **stale 40-key** version; missing `delta`, `curr_rank`, `level_delta`,
  `chess_synergies`, `relic`, `ban_synergy`. **Never use for live state** — use
  `player_info_table.player_info` (full 46 keys).
- `user_panel_ranking` — thin `{steam_id: {curr_rank}}` map (redundant; `curr_rank` is in
  every player object).
- `show_all_player_connect_status` — `{slot: 0|1}` connect bitmap (inferable from
  `death_team`/`hp`).
- sometimes `stat_chess`, `game_over` at POST_GAME.

## 3. Field semantics (the 46-key player object)

### Synergies — use `chess_synergies`, NOT inference, NOT `show_buff`
- **`chess_synergies`** = the game's authoritative list of **activated** synergies
  (breakpoints met), numbered. The `1` suffix = a higher tier: `is_knight` + `is_knight1`
  both present = Knight at its 2nd breakpoint. **Normalize** `is_X`/`is_X1` → "synergy X,
  tier N". Use this for display/analysis — it already bakes in multi-trait units,
  trait-granting items, summons, etc. Do **not** re-derive synergies from `chess_lineup`
  (reinvents the synergy engine, worse accuracy).
- **`buff`** = raw unit-count per trait (incl. below-breakpoint count-1 traits). Use ONLY
  if we want a "near next breakpoint" indicator.
- **`show_buff`** = **STALE JUNK.** Identical for all 8 players
  (`is_beast:4,is_hunter:3,is_druid:2,is_centaur:2`) and matches nobody's board. Do not
  store. (Same smell as the `hehe` random nonce and stale `dac_table.player_info`.)

### MMR / rewards
- `delta` = MMR change this game. `level_delta` = MMR-level change. `mmr_level` = final
  rank tier. `candy_award` = candy earned this game. `candy` = lifetime total (in
  player_info_table) vs awarded (in end_board) — different meaning per table.

### Carry summary
- `lineup_value` / `max_lineup_value` = board strength (summed unit worth, star-weighted);
  `max_lineup_value_lineup` = comp string at the peak. (Note: highest value ≠ winner — a
  2nd-place Void board can out-value the winner.)
- `mvp_chess_name` = highest-damage unit. Star suffix: none = 1★, `1` = 2★, `11` = 3★
  (e.g. `chess_void11` = 3★ Faceless Void).
- `mvp_chess_damage` = that unit's total damage.
- `mvp_chess_items` = comma-separated internal item IDs on the MVP (empty if none); resolve
  via `content/` pipeline like other item IDs.

### Other usable per-player fields
- `hero_damage` / `hero_damaged` (dealt / taken), `kills` / `deaths`.
- `pandaman_getlist` = panda-drop units received (1 for one player, 25 for a Void roller).
- `talent_tree` = `{n: talent_id}` picks.
- `relic` (active) + `relic_history` = `{n: {relic, round}}` full relic-pick timeline.
- `win_round` / `lose_round` / `draw_round`, `hero_level`, `total_money`, `duration`,
  `rank` (final placement) / `curr_rank` (live standing), `chess_lineup`, `chess_hand`.

## 4. `end_board` capture reliability (the real bug to fix)

Problem: capture is inconsistent because the keystroke driver needs Dota **foreground**
(netconport is dead on Windows), and observers alt-tab / leave when eliminated.

Facts that make it tractable:
- `end_board` **persists** in `dac_table` after game-over until the observer leaves —
  there's a seconds-to-minutes window to grab it, not a single instant.
- **GSI post-game** is focus-independent (HTTP push from Dota) — reliable game-over signal
  even when alt-tabbed.
- DAC lets you **spectate to the end** after elimination — the client keeps receiving
  nettable updates if you don't quit.

**Implemented fix:**
1. On GSI post-game (and manual "Check active match"), **force Dota to foreground**
   (`SetForegroundWindow` + `AttachThreadInput` to beat the foreground lock), fire
   the dump burst to lift `end_board`, restore the previous foreground window.
2. **Don't stop capture on the observer's own elimination** — keep going until `end_board`
   or disconnect.
3. **Drop end-lobby screenshots** entirely — structured `end_board` replaces them (the dead
   `screenshots` storage bucket is a leftover of this).

Live cadence still does **not** steal focus every few seconds (that would be miserable);
only critical dumps do.

### Hard constraint (input requires focus)
Effectively, input can't reach the Dota window unless it is focused/foreground — for any
method we can responsibly use:
- `PostMessage`/`SendMessage` (WM_KEYDOWN) deliver without focus but Source 2 reads keyboard
  via the **Raw Input API**, which ignores synthetic window messages → game never sees them.
- `SendInput`/`keybd_event` inject into the system input stream, which Windows routes to the
  **foreground window only** → requires focus.
- Windows routes keyboard input by focus all the way down (even a kernel driver / virtual HID
  delivers to the foreground window), so there's no "aim a keypress at an unfocused window"
  primitive.
- The only true bypass is DLL-injecting `dota2.exe` / writing its input state directly —
  **VAC-bannable, off the table.**
- netconport (socket console, focus-free) is dead on Windows.

**Current approach is in the VAC-safe lane** (keep it there): VAC inspects the *game process*
(injection, memory read/write, code patching). Our pipeline does none of that — `SendInput`
is external synthetic input (indistinguishable from a real keypress; same as any macro tool),
`console.log` is a passive file read (`-condebug`), `dumpstringtable` is a built-in dev
command, GSI is official. No injection, no memory access = nothing VAC patterns. The
match-history *memory-read* idea was the only thing that would have crossed the line; that's
why it stays shelved. (Not a forever-guarantee — Valve policy is opaque — but correct by
VAC's current design.)

So every dump needs Dota foregrounded at the instant the keystroke fires → focus-steal is
mandatory when the user isn't already in Dota. (Basis: Windows input + Source Raw Input
internals, not a session test — but matches observed "background keys do nothing" behavior.)

**Detection vs action are decoupled:**
- *Detecting* game state (round change, POST_GAME) is **free and focus-independent** — GSI
  HTTP push + console.log tailing. We always know *when* to dump.
- *Acting* (the dump) always needs focus. We cannot escape this by moving the loop into the
  console: Dota disables `wait` (the frame-delay primitive every Source console loop needs),
  recursive `alias` without `wait` runs instantly (no timer), and there is no
  "on game event → run console command" hook for the client console in a signed custom game.
  Binds only fire on real key input; GSI is read-only and can't trigger commands. So the
  cadence must live in our backend keystroke driver, gated by focus.

### Idea: tab-out duration → fallback `player_info` dump (revisit)
Track how long Dota has been **unfocused** (tabbed out). If it exceeds X seconds, fire a
normal `player_info_table` dump as a safety snapshot — in case we missed the user leaving,
or they're about to leave/AFK and we'd otherwise lose their final state.

- Caveat from the constraint above: this fallback dump **also requires a brief focus-steal**
  (you can't dump while tabbed out without focusing Dota first). So it's a deliberate,
  disruptive focus-steal traded for not losing the capture. The tab-out duration X is the
  knob that decides when that disruption is worth it.
- Open: pick X; decide whether to also re-fire on tab-back-in; confirm GSI still gives us a
  clean game-over even when the user never tabs back.
